# ADR 0049：有界的宿主启动与首屏衔接

- 日期：2026-10-12

## 决策

宿主启动时统一记录核心准备、插件恢复、页面是否已经显示，以及失败原因。核心准备包括本地数据、默认主题验证和宿主更新事务的保护。25 秒内没有完成，就明确失败。Android 更新器的状态和事件恢复共用 3 秒上限。状态还不知道时，不能继续写入宿主代次，也不能放开更新锁。

核心准备完成之后再挂上页面外壳。插件恢复作为普通任务启动：先恢复兼容的本地安装缓存，再补上缺少的预装项。完整初始化失败时，错误传给调用方，同一次会话里不自动重试。插件恢复最多等 10 秒。超时之后可以明确选择先进入课表；这之后才到的注册，不能覆盖用户已经选好的页面。更新，以及恢复初始状态，都要求完整启动已经成功。

正常启动仍然等插件恢复完成，再进入声明的默认首页，不先显示课表再跳转。非关键页面的预热可以使用带 1000 毫秒超时的空闲回调。关键的启动步骤不能靠空闲回调。

Android 的原生启动屏在本地主文档或错误页加载完成之后关闭，并有 8 秒兜底；Activity 销毁时也会清理。网页上的启动遮罩在加载结束、失败，或目标页面的内容已经挂上，并且经过一次 Svelte 更新和一帧动画之后关闭，避免露出没有内容的背景。

## 超时与验证边界

等待超时不等于取消底下还在跑的插件或原生工作。不要把仍在执行的操作再启动一次，也不接受迟到的结果把失败状态改掉。重试通过重新加载页面，开始新的会话。已有的安装记录、更新协议和数据库结构保持不变。

阶段失败使用现有的错误捕获、回放和日志插件。阶段完成用 Performance 标记记录，不新增持久化的日志库。浏览器里受控的调度测试，和 Android 真机上的冷启动，要分开报告。把空闲回调模拟成一直不执行，不能用来证明某台 WebView 上的真实故障原因。

本地数据必须读成功才算核心准备完成，这条边界已由 [ADR 0050](0050-error-contracts-and-failure-boundaries.md) 收紧：核心准备会等课表列表和当前课表都读取成功。读取失败不能用「没有课表」或默认配置代替。

## Android 原生启动 Profile

Release 构建使用 `apps/mobile/android/app/src/main/generated/baselineProfiles/` 里已经提交的 Baseline Profile 和 Startup Profile。前者通过 ProfileInstaller，让侧载的 APK 也能走 ART 的配置编译；后者交给 R8，用来调整启动代码的 DEX 布局。它们优化的是原生宿主，不是 WebView 里的 JavaScript 和 CSS。普通的 Release 构建不会为了这个去启动模拟器。CI 会检查 APK 里有编译后的 Profile 和错误页，并且没有 PWA 专用资源。

原生启动路径，或者 Capacitor、AndroidX 依赖有变化时，先运行 `vp run mobile:build`。然后连接 API 33 或更高版本的设备或模拟器；已经 root 的 API 28 或更高版本也可以。确认 WebView 达到应用要求的最低版本后，在 `apps/mobile/android` 运行：

```sh
./gradlew :app:generateBaselineProfile
```

采集模块 `:baselineprofile` 使用单独的 debug 签名和 `nonMinifiedRelease` 变体。它会启动应用，等到实际界面出现，不使用正式签名密钥。生成的两份文本 Profile 要检查后再提交。正式的 Release APK 和 AAB 仍然必须配置官方签名用的环境变量。Profile 只来自采集到的启动场景，性能是否有改善，需要在真机上测量，不能从模拟器采集结果推断。

当前提交的 Profile 是 2026-10-02 在 Android 15（API 35）、ARM64 Pixel 6 模拟器和 WebView 124 上采集的，覆盖从冷启动到欢迎页或课表可见。课表导入、页面切换等后续操作没有覆盖。
